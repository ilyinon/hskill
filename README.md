# HackSkills

Набор из **103 скиллов для AI-агентов**, которые помогают проводить аудит безопасности, исследовать уязвимости, разбирать инциденты и решать лабораторные задачи. Общая точка входа — [`hack`](skills/hack/SKILL.md): она задаёт порядок работы, требования к доказательствам и выбор нужной специализации.

В наборе есть методики, примеры, справочники и шаблоны отчётов. Агент выбирает технику по задаче и наблюдаемым данным, проверяет её предпосылки и отделяет подтверждённый результат от гипотезы.

## Быстрый старт

Разместите репозиторий там, где агент может читать локальные файлы. Если скиллы уже подключены в вашей среде, вызывайте главный `hack`. Также можно явно передать агенту путь к `skills/hack/SKILL.md`:

```text
Прочитай skills/hack/SKILL.md.
Проведи локальный аудит ./src на ошибки объектной авторизации.
Покажи путь проверки прав и ссылки на участки кода, которые подтверждают выводы.
```

Для анализа полезно сразу передать исходники, конфигурацию, дамп, захват трафика или описание наблюдения. Перед активным тестированием укажите разрешённые цели, действия и ограничения; уже согласованные условия используются повторно.

Главный `hack` выбирает нужную ветку. Если тема известна, агент может сразу открыть соответствующий специализированный `SKILL.md`. Для поиска подходящей темы есть [технический указатель](skills/hack/ROUTING.md).

## Как устроена загрузка

```text
skills/
├── hack/
│   ├── SKILL.md          # Общие правила и выбор ветки
│   ├── ROUTING.md        # Поиск технической специализации
│   └── *.md              # Методики для отдельных рабочих сценариев
└── <topic>/
    ├── SKILL.md          # Подход, доказательства, ограничения и ссылки
    ├── references/       # Подробные техники, примеры и таблицы
    └── *.md              # Дополнительные тематические справочники
scripts/
└── check_skills.py       # Проверка структуры и ссылок
tests/
├── test_reference_examples.py
└── eval_cases.json
```

Короткие специализации могут целиком помещаться в `SKILL.md`. В крупных темах подробности вынесены в справочники; часть дополнительных материалов сохранена рядом с входным файлом.

Обычный путь чтения: **`hack` → нужная специализация → справочник для текущего шага**. Ролевые методики и указатель подключаются, когда помогают задаче. Такой порядок экономит контекст: агенту не требуется заранее читать весь набор или каждый связанный документ.

В десяти специализациях — SSRF, SQLi, IDOR, бизнес-логике, JWT, OAuth/OIDC, XSS, ROP, симметричной криптографии и PCAP — доступны два дополнительных справочника:

- `references/diagnostics.md`: предпосылки техники, объяснения наблюдений, различающие проверки и условия завершения задачи.
- `references/worked-cases.md`: законченный учебный разбор с неудачным первым подходом, пересмотром гипотезы, результатом и независимыми контрольными проверками.

Эти файлы открываются по необходимости. Примеры включают локальные исходники и данные, а проверки имеют явно указанные границы: расчёт стека не означает выполненную ROP-цепочку, разбор разметки не доказывает исполнение JavaScript в браузере.

## Требования к результату

- Указывать проверяемую границу доступа, участника, объект и ожидаемое поведение.
- Сопоставлять наблюдение с исходным состоянием и контрольной проверкой. HTTP 200, ошибка, отражение ввода или срабатывание сканера сами по себе остаются зацепками.
- Для аудита кода прослеживать фактический путь данных и проверок; достаточное доказательство в исходниках может обосновать вывод без обращения к production.
- Отдельно отмечать подтверждённые факты, гипотезы и непроверенное влияние. Неисследованную область учитывать как непокрытую.
- Выбирать минимальное достаточное доказательство и завершать проверку, когда оно получено в согласованных пределах.

Применимость примеров зависит от версии, конфигурации и доступных возможностей. Исторические таблицы и каталоги гаджетов требуют проверки этих предпосылок; они не гарантируют работоспособность техники на конкретной цели.

## Проверка набора

Для проверяющих скриптов нужен **Python 3.9+**. Запускайте команды из корня репозитория:

```sh
python3 scripts/check_skills.py
python3 scripts/eval_skills.py validate
python3 -m unittest discover -s tests -v
```

Первая команда проверяет метаданные, локальные Markdown-ссылки, якоря, закрытие блоков кода и достижимость справочников из входных файлов. Базовая проверка работает офлайн и использует стандартную библиотеку; установленный `PyYAML` включает полный разбор YAML.

Для оценки размера входных файлов дополнительно нужен `tiktoken`:

```sh
python3 scripts/check_skills.py --tokens
```

Текущий порог для пересмотра входа — **1 600 токенов**. Это внутренний ориентир сопровождения. Подсчёт использует `o200k_base` и охватывает текст файлов; расход всей сессии также зависит от истории, инструментов и выбранных справочников. При первом подсчёте токенизатор может скачать таблицу кодирования.

Автотесты проверяют выбранные математические примеры, локальные модели авторизации, JWT и OAuth, а также структуру бинарных артефактов. В [`tests/eval_cases.json`](tests/eval_cases.json) находятся **28 поведенческих сценариев с исходниками и артефактами**. Команда ниже готовит входы без ожидаемых ответов:

```sh
python3 scripts/eval_skills.py prepare --output /tmp/hack-blind-001
```

Десять сценариев `solve-*` используют другие данные или условия, чем учебные разборы. Они проверяют выбор подхода, корректное опровержение гипотезы и получение конкретного результата, включая предсказание чисел и восстановление потока.

Порядок независимой проверки, сохранения ответов, оценки ложных срабатываний и сравнения прочитанного контекста описан в [tests/EVALUATION.md](tests/EVALUATION.md). Выборочные источники, даты, проверенные окружения и ограничения техник записаны в [реестре проверки](skills/hack/verification.json). Эти проверки не охватывают выполнение всех эксплуатационных примеров и каждую указанную версию ПО.

[GitHub Actions](.github/workflows/skills.yml) запускает проверки структуры, офлайн-тесты и сравнение размеров входов и справочников с [базовой версией](tests/token_baseline.json). Поведенческая оценка агентом выполняется отдельно; CI не обращается к модели или тестовой цели.
